# 크레타 광고 4단계 — 화면(디바이스) 타기팅 (2026-08) — ✅ 구현됨(2026-08-26)

[creta-ad-platform-plan-2026-08.md](creta-ad-platform-plan-2026-08.md) 의 1~3단계에 이어,
**"이 캠페인을 어느 화면에 내보낼지"** 를 정하는 축을 넣는다.

## 왜 지금인가

1~3단계는 하루에 만들어졌고(`322a13c` → `cda00ab` → `746b31c`), 디바이스 타기팅은 그때 두 번
연속으로 미뤄졌다. 계획 문서에 사유가 남아 있다.

> SOV(%) 점유율·시간당 재생 상한·**디바이스 태그 타기팅**(위젯이 디바이스 문맥을 모르는 시뮬레이션 한계)

당시엔 맞는 판단이었다. 실제 플레이어가 없어 광고가 "재생되는 장소"가 북 미리보기뿐이었고,
거기엔 디바이스 개념이 없었다. 그 사이 두 가지가 달라졌다.

**① 디바이스 문맥이 생겼다.** 디바이스 상세 화면은 이미 프레젠테이션을 iframe으로 띄운다
(`/books/{id}/preview?embed=1`). 즉 "이 화면이 이 북을 재생 중"이라는 문맥이 실제로 존재하는데
URL에 디바이스를 안 넘기고 있을 뿐이다. 디바이스 태그도 이미 쓰이고 있다.

**② 3단계가 모순을 만들었다.** 구좌 인벤토리가 "연결 디바이스 수 × 시간당 노출 능력"을 계산하기
시작하면서 **재고는 화면 단위로 세는데 판매는 구좌 단위로 하는** 상태가 됐다. 같은 구좌라도
그 북이 몇 대에 깔렸느냐에 따라 가치가 달라지는데, 광고 시스템은 그걸 모른다.

## 지금 상태의 문제 (코드 확인)

| #   | 문제                                 | 근거                                                                                                                                   |
| --- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 캠페인이 나갈 화면을 못 정한다       | `listActiveCreatives()` 가 인자를 받지 않는다 — 디바이스·북·구좌를 전혀 모른다                                                         |
| 2   | 노출 로그에 화면이 없다              | `creta_ad_play_log` 에 `deviceId` 없음. "로비 화면에서 400회"를 증명할 수 없다                                                         |
| 3   | 광고 전용 루프가 리포트에서 투명하다 | `logCretaAdPlay` 호출부가 구좌 위젯·프레젠테이션 두 곳뿐이고, 재생 이력 백필(`resolveContents`)도 `sourceType="ad"` 를 처리하지 않는다 |

3번이 특히 나쁘다. 광고 전용으로 돌리는 디바이스는 **재생 리포트에도, 광고 리포트에도 안 잡힌다.**

## 설계 결정

### 타기팅 축은 디바이스 태그로 한다

옥외·매장 광고(DOOH)에서 파는 단위는 **화면**이다. 광고주는 "로비 스크린 5대, 4주, 점유율 20%"
같은 식으로 사지, "위젯 자리"를 사지 않는다. 위젯 자리는 **규격**(크기·길이)이지 재고가 아니다.

구좌(위젯) 단위 타기팅이 지금 당장은 더 쉽다 — 위젯이 이미 `bookId`·`slotElementId`를 안다.
그래도 택하지 않는다. 북 하나가 여러 디바이스에 깔리면 "어디에 나가는지"를 여전히 통제할 수 없고,
결국 화면 타기팅을 다시 해야 한다.

디바이스 태그는 이미 있고(층·구역·방향 등), 한 디바이스가 여러 태그에 속할 수 있어
그룹 타기팅에 그대로 쓸 수 있다.

### 위젯(존)형 채널은 유지한다

"광고를 북 위젯이 아니라 디바이스 소스로 했어야 하지 않나"는 질문이 있었는데, 그 방식은
이미 있다(`sourceType="ad"` 광고 전용 루프). 그리고 위젯형도 업계 표준이다 — Xibo의
Layout→Region, Broadsign의 frame에 해당하고, 크레타에서는 북=레이아웃, 광고 위젯=리전으로 정확히 대응한다.

두 채널은 파는 물건이 다르다.

- **전체화면 스팟** — 광고만 나가는 시간 (루프 삽입 · 광고 전용)
- **상시 구좌** — 콘텐츠와 같이 떠 있는 자리 (메뉴보드 옆 배너 등)

메뉴보드를 보여주면서 옆 자리를 파는 건 위젯형으로만 된다. 걷어내지 않는다.

### 디바이스 문맥은 프레젠테이션 URL로 전달한다

프레젠테이션(`/books/{id}/preview`)이 곧 플레이어 시뮬레이션이다. 여기에 `?device={id}` 를 더해
"지금 이 화면을 흉내내는 중"을 알린다. 디바이스 상세의 iframe이 이 값을 넘기면
**세 채널(구좌 위젯 · 루프 스팟 · 광고 전용) 전부**가 같은 문맥을 갖는다.

`?device` 가 없으면(북 편집기·일반 북 보기) 지금처럼 전체 후보를 보여준다 — 화면에 매이지 않은
"편성 후보 전체" 미리보기다.

## 구현 항목

### 1. 스키마 (마이그레이션 0022) — ✅

```
creta_ad_campaign_target
  id          serial PK
  campaignId  integer NOT NULL → creta_ad_campaign(id) ON DELETE cascade
  tag         varchar(40) NOT NULL
  UNIQUE(campaignId, tag) · INDEX(campaignId)

creta_ad_play_log
  + deviceId    integer          -- FK 없음(기존 로그 규칙: 삭제돼도 리포트 유지)
  + deviceName  varchar(120)     -- 비정규화
  + INDEX(deviceId, playedAt)
```

**대상 행이 없으면 = 전체 화면 대상.** 기존 캠페인은 손대지 않아도 지금과 똑같이 동작한다.

### 2. 편성 필터 — ✅

`listActiveCreatives(ctx?: { deviceId?: number })`

- `ctx.deviceId` 있음 → 그 디바이스의 태그를 읽어, **대상이 없는 캠페인 + 태그가 겹치는 캠페인**만
- `ctx.deviceId` 없음 → 지금처럼 전부 (편성 후보 전체)

기존 필터(기간·상태·요일·시간대·시간당 상한·심의)는 그대로 앞단에 둔다.

### 3. 노출 로그에 화면 기록 — ✅

`logPlay(input)` 에 `deviceId` 추가 → 디바이스 이름을 찾아 비정규화 저장.
호출부 세 곳 모두 전달한다.

| 호출부                                | 구좌 id    | 디바이스                  |
| ------------------------------------- | ---------- | ------------------------- |
| `BookAdSlotWidgetOverlay` (구좌 위젯) | 요소 id    | `?device` 가 있으면 그 값 |
| `BookPresentationPage` (루프 스팟)    | `"loop"`   | 〃                        |
| `DeviceDetailPage` (광고 전용 루프)   | `"adloop"` | 현재 디바이스             |

### 4. 광고 전용 루프 속 채우기 — ✅

- `creta-play-log.service.ts` 의 `resolveContents` 에 `sourceType === "ad"` 케이스 추가 →
  재생 리포트에 "광고 전용 루프"로 집계된다
- 디바이스 상세의 광고 전용 카드가 소재를 실제로 순환시키고 노출 로그를 남긴다

### 5. 리포트·인벤토리 — ✅

- **디바이스별 노출** 섹션을 재생 리포트 광고 영역에 추가 (캠페인별·시간대별·구좌별 옆)
- **인벤토리를 화면 기준으로 재구성** — 구좌별 표 대신 "디바이스 × 시간당 노출 능력"을 기준으로,
  태그별로 묶어서 보여준다. 구좌는 그 안의 규격으로 표시한다

### 6. 관리 화면 — ✅

- 캠페인 만들기·수정에 **대상 태그 선택**(디바이스 태그 목록에서 다중 선택, 비우면 전체)
- 캠페인 카드에 `대상: 전체` 또는 `대상: 로비 · 카페` 표시
- 감사 로그에 대상 변경 기록

## 범위 밖

- 광고주 계정 초대(자기 캠페인 리포트만 열람) — 3단계에서 "남김(선택)"으로 둔 그대로
- 프로그래매틱(실시간 입찰) — 1단계 문서에서 이미 범위 밖으로 정함
- 화면별 SOV 보장 — 지금은 네트워크 전체 가중치 기준 %만 표시. 화면별 보장은 실제 플레이어가
  생긴 뒤에 다룬다

## 구현 메모 (2026-08-26)

- 마이그레이션 번호는 계획의 0021이 아니라 **0022**가 됐다(도커 기동 수정으로 넣은
  `0002_1_creta_baseline` 때문에 저널 인덱스가 하나 밀림).
- 로테이션 로직을 `src/lib/creta-ad-rotation.ts` 로 추출했다. 구좌 위젯과 디바이스
  광고 전용 루프가 같은 가중 라운드로빈·공통 클록을 쓴다(단위 테스트 8개).
- 인벤토리는 `slotInventory()` → `screenInventory()` 로 교체했다. 플레이리스트·스케줄을
  거쳐 재생되는 북의 구좌까지 해석해, 3단계가 "근사치"라고 적어 둔 한계를 없앴다.
- 캠페인 수정 UI가 원래 없어서(일시중지/재개만 있었다) 카드에 대상 편집 팝오버를 붙였다.
- 재생 이력 `contentKind` 에 `ad` 가 생겨 리포트·대시보드 배지 라벨 매핑을 함께 넓혔다.

### 검증

- 단위 테스트 100개 통과(로테이션 8개 신규)
- 화면 인벤토리의 "캠페인" 수가 10개 화면 전부 손으로 계산한 값과 일치
- `?device=` 를 붙인 프레젠테이션에서 루프탑(루프탑 타깃 캠페인 노출됨) vs
  주차장(3회 샘플 모두 전체 대상 캠페인만) 로 타기팅 동작 확인
- 광고 전용 루프가 `slotElementId="adloop"` 로 노출을 기록하고, 재생 이력에도
  "광고 전용 루프"로 400건 집계되는 것 확인 — 이전에는 두 리포트 모두 0이었다
